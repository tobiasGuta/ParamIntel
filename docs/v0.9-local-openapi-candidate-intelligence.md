# ParamIntel v0.9 — Local OpenAPI Candidate Intelligence

v0.9 adds OpenAPI as a **deterministic candidate-intelligence source**, not as a vulnerability oracle or a generic API scanner.

The governing rule is:

> OpenAPI may tell ParamIntel what is worth testing and where it may belong. The live application, repeated probes, and paired random-name controls remain the only authority for behavioral findings.

## Why this is narrow

Existing OpenAPI tooling already performs broad endpoint generation, schema fuzzing, and request generation. ParamIntel's useful role is different: derive a small set of high-signal JSON parameter hypotheses, preserve their provenance, and eventually pass them through the same verifier used by every other ParamIntel candidate.

v0.9 therefore does not treat schema declarations as runtime truth. `readOnly`, `writeOnly`, `required`, declared types, and schema membership are candidate metadata. They do not raise confidence and do not create a finding.

## Parser decision

The v0.9 research spike compared Go-compatible OpenAPI parsers under ParamIntel's Go 1.23 baseline.

The first production slices pin:

```text
github.com/pb33f/libopenapi v0.25.0
```

The decisive compatibility case was a normal OpenAPI 3.1 / JSON Schema union:

```yaml
type:
  - string
  - 'null'
```

The checked Go-1.23-compatible `kin-openapi` candidate rejected that fixture, while `libopenapi v0.25.0` preserved both declared types.

Basic OpenAPI 3.2.1 documents parsed in the spike, but ParamIntel does **not** claim complete OpenAPI 3.2.1 semantic support from that result.

## Local-only document boundary

The production parser configuration is deliberately restrictive:

- the caller supplies OpenAPI bytes locally;
- file references are disabled;
- remote references are disabled;
- no BasePath is configured;
- no BaseURL is configured;
- internal references are allowed;
- an unresolved/external reference affecting the model causes schema intelligence to fail closed;
- the parser is not allowed to discover or download specifications automatically.

## Operation selection

Schema intelligence starts from the already-captured HTTP request.

1. Parse the captured request URL path and method.
2. Prefer an exact concrete OpenAPI path.
3. Otherwise match templated paths.
4. If more than one template matches the same method/path, reject schema intelligence as ambiguous.
5. Never let parser map ordering choose an ambiguous operation implicitly.

Example:

```text
PATCH /users/me
```

prefers an exact `/users/me` operation over `/users/{id}`.

But:

```text
/users/{id}
/users/{name}
```

matching the same captured request is ambiguous and must be rejected.

## Request schema selection

v0.9 starts with JSON request bodies only.

The captured request's `Content-Type` selects the operation's request media type. Parameters such as `charset=utf-8` are normalized. Exact media types outrank wildcard media ranges.

Non-JSON request media types are outside this first release boundary.

## Response schema selection

The already-collected stable ParamIntel baseline selects the response schema.

Response selection order is:

```text
exact status code
    ↓
status class (for example 2XX)
    ↓
default response
```

The baseline response content type then selects the response media type.

Schema intelligence requires a stable baseline status and stable content type. An unstable baseline does not get interpreted through an arbitrary schema branch.

## Bounded schema walking

The initial walker supports:

- object properties;
- internal `$ref` resolution;
- `allOf` branches at the same JSON location;
- declared JSON types, including OpenAPI 3.1 multi-type declarations;
- `readOnly`, `writeOnly`, and `required` as metadata.

The walker is bounded by configurable maximum depth and maximum schema-node count.

Additional rules:

- reference cycles are detected with an active reference stack;
- arrays are recorded as structure but not traversed for candidates;
- `oneOf` and `anyOf` subtrees are skipped as ambiguous in the initial policy;
- object containers provide placement context but are not whole-object candidates.

## Primary candidate class

The first v0.9 candidate source is:

```text
openapi_response_only_json_property
```

A property qualifies structurally when it appears in the selected response schema but not in the selected request schema.

Example:

```text
request schema
└── $.profile.name

response schema
├── $.profile.name
├── $.role
└── $.profile.settings.beta_access
```

Potential descriptors:

```text
$.role
  source: openapi_response_only_json_property
  placement: existing_parent

$.profile.settings.beta_access
  source: openapi_response_only_json_property
  placement: one_level_scaffold
  scaffold parent: $.profile.settings
```

These are hypotheses only.

## Placement classification

The passive representation layer also compares a hypothesis with the captured JSON body.

### Existing parent

If the candidate's parent already exists as an object in the captured request:

```text
placement = existing_parent
```

### One-level scaffold

If exactly one parent object is absent, the direct ancestor exists as an object, and the response schema describes that missing parent as an object:

```text
placement = one_level_scaffold
```

This classification does **not** authorize mutation. A later slice must explicitly extend v0.8's scaffold provenance gate before an OpenAPI-derived scaffold can be sent.

### Rejected placements

The passive layer skips candidates when:

- the parent location is occupied by a scalar, `null`, or array;
- more than one parent level is missing;
- the parent structure is ambiguous;
- the candidate itself is an array or whole-object container;
- the property is already present in the captured request.

## Slice 1 boundary

v0.9 Slice 1 is intentionally passive.

It adds:

- local-only OpenAPI parsing;
- exact/templated operation matching;
- request/response media selection;
- bounded schema property extraction;
- response-only candidate descriptors;
- placement/scaffold classification;
- deterministic provenance metadata.

It does **not** add:

- an `-openapi` CLI flag;
- file loading from the CLI;
- discovery seed injection;
- OpenAPI scaffold authorization;
- target requests;
- confidence changes;
- evidence changes;
- enum/default/example probing;
- endpoint enumeration;
- arrays or multi-level scaffold synthesis.

Those boundaries let the representation be reviewed and tested before OpenAPI metadata can influence active discovery.
