# v0.11 Evidence-Guided Adaptive Rescue

## Goal

Use ParamIntel's bounded semantic-rescue request budget where the target application provides the strongest evidence that a candidate is worth deeper testing.

The design does not change the core trust model:

> AI proposes what is worth testing; ParamIntel proves whether it matters.

Candidate ordering may change. Verification, negative controls, confidence scoring, and finding admission do not.

## Why this exists

v0.10 can have many value-aware rescue candidates but a small shared request budget. Current ordering can spend that budget on weak generic candidates before stronger application-backed candidates.

v0.11 treats request budget as a scarce resource.

## Evidence tiers

The first scheduler slice uses deterministic tiers:

| Tier | Meaning | Examples |
| --- | --- | --- |
| A | direct application evidence | OpenAPI response-only property, actionable context-response property |
| B | contextual / structural evidence | scaffoldable response-derived property, explicit contextual semantic match |
| C | AI candidate hypothesis | locally admitted Gemini candidate |
| D | local semantic heuristic | built-in profiles such as `debug`, `limit`, `format` |
| E | generic only | candidate with no stronger evidence |

Ordering is lexicographic rather than a single opaque weighted score:

1. evidence tier;
2. candidate-source priority;
3. contextual semantic relevance;
4. lower deterministic clean-miss screening cost when evidence is otherwise equal;
5. stable existing order when all evidence is equal.

Contextual semantic relevance is local and deterministic. ParamIntel derives it from the sanitized baseline response shape, or from an explicit `-context-response` when present. This ranking path does not require Gemini, an API key, or any provider call.

A model confidence value never outranks stronger deterministic application evidence.

## Slice 1: evidence-guided ordering

Implemented on `feat/v0.11-evidence-guided-rescue`.

Behavior:

- all value-aware eligible candidates are ranked before semantic rescue;
- application-backed candidates can overtake earlier AI/generic candidates;
- existing `CandidateSource.Priority` is reused instead of inventing a second priority system;
- optional contextual relevance remains a deterministic secondary signal;
- verbose mode prints the resulting rescue order and reason;
- semantic values, request execution, paired controls, repeated verification, confidence, and finding admission are unchanged.

Acceptance test:

A deliberately first-listed AI candidate and a later application-backed candidate compete for an eight-request budget. The application-backed candidate must receive the budget first and verify successfully.

## Slice 2: request accounting

Implemented.

The report now records per-candidate rescue accounting without changing rescue behavior:

- evidence tier;
- source priority;
- contextual relevance;
- deterministic value count;
- whether Gemini was queried;
- number of admitted AI values;
- remaining budget before/after;
- total rescue requests consumed;
- outcome: verified, miss, or budget exhausted;
- discovery mode for verified parameters.

The top-level value-aware summary records:

- configured rescue budget;
- requests used;
- requests spent on verified candidates;
- requests spent on clean misses;
- requests spent on budget-exhausted partial attempts;
- eligible candidates;
- candidates attempted;
- candidates deferred because execution stopped before reaching them;
- verified parameters.

This creates measurement before optimization.

## Slice 3: safe verification-feasibility guard

Implemented.

v0.11 stops starting new semantic values when the remaining request budget cannot possibly support:

- the candidate screen;
- its paired random-name control;
- the configured repeated candidate/control verification.

With the default three trials, this floor is eight requests.

This rule is intentionally narrower than semantic-profile truncation. It cannot remove a finding that was still fully verifiable under the remaining configured budget.

The frozen zero-signal control moves from 60 legacy/static requests to 57 requests with the guard enabled.

Aggressive priority decay or profile truncation is **not** enabled. The current evidence does not justify the recall risk.

## Slice 4: evaluation — complete

v0.11 was evaluated against frozen localhost fixtures plus authorized external training/API targets.

Primary observations:

- **Tight-budget recall improved.** In controlled cases where a high-signal candidate would otherwise appear too late, evidence-guided ordering converted an eight-request budget from no finding into a fully verified finding.
- **Already-favorable ordering did not regress.** When the strongest candidate was already first, v0.10 and v0.11 verified the same behavior at the same rescue cost.
- **Application evidence outranked AI provenance.** Deterministic target evidence received scarce rescue budget ahead of an earlier AI hypothesis.
- **Zero-signal cost improved modestly, not dramatically.** The safe verification-feasibility floor reduced the 17-candidate control from 60 to 57 rescue requests without removing a finding that remained fully verifiable.
- **OWASP crAPI false-positive controls held.** A real authenticated endpoint reproduced the 57/64 tail behavior with zero findings. Context-backed Gemini prioritization promoted `role` without producing a false finding. OpenAPI coupon hypotheses were rejected when paired random-name controls reproduced the same behavior.
- **Body-less OpenAPI handling remained conservative.** A GET operation without a request body could contribute operation/response-schema intelligence, but no writable JSON candidates were invented.
- **PortSwigger positive recall succeeded.** In the Web Security Academy mass-assignment lab, response-derived `$.chosen_discount` and one-level-scaffolded `$.chosen_discount.percentage` both verified at 3/3 candidate changes versus 0/3 random-name control changes.

Graduation result:

> v0.11 keeps or improves verified-parameter recall in the measured cases while making bounded rescue allocation more evidence-aware and eliminating only an unverifiable request-budget tail.

The evaluation does **not** justify aggressive semantic-profile truncation, reinforcement learning, provider-confidence scoring, or looser verification. Those remain out of scope for v0.11.

## Non-goals

v0.11 is not:

- a reinforcement-learning scheduler;
- a Jev replacement;
- an autonomous vulnerability judge;
- a provider-confidence ranking system;
- a rewrite of ParamIntel's verifier;
- an excuse to loosen finding confidence or negative controls.
