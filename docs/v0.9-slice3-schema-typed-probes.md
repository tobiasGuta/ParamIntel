# ParamIntel v0.9 Slice 3 — Schema-Typed Scalar Probes

Slice 3 lets a narrow subset of local OpenAPI metadata influence **probe value type only**.

The authority invariant remains unchanged:

> OpenAPI may influence what ParamIntel tests and the JSON scalar type used for a probe. Only live application behavior, repeated trials, paired random-name controls, and existing confidence/evidence rules may produce a finding.

## Why this slice exists

Slice 2 admitted response-schema-only JSON properties whose parent already exists in the captured request. Those candidates still entered discovery with the generic random string value used by historical ParamIntel discovery.

That can create a conservative false negative when an API accepts a hidden field only if its JSON type is valid. For example, a schema may declare:

```yaml
beta_access:
  type: boolean
```

while the server silently ignores:

```json
{"beta_access":"random-string"}
```

but reacts to:

```json
{"beta_access":true}
```

If the first-pass filter uses only a string, the candidate can be discarded before repeated verification ever sees a valid typed value.

## Supported types

Slice 3 is intentionally narrow.

An OpenAPI-derived JSON candidate receives a schema-typed probe only when its applicable candidate provenance contains exactly one declared type and that type is one of:

```text
boolean -> true
integer -> 1
```

The selected value is a ParamIntel-owned neutral representative. It is not copied from the OpenAPI document.

The following remain on the existing generic string path:

- `string`;
- `number`;
- `null`;
- multi-type/union declarations such as `[boolean, null]`;
- arrays;
- objects;
- candidates without OpenAPI response-only provenance;
- context-response candidates;
- AI candidates;
- generic wordlist candidates.

## No schema value consumption

Slice 3 does not read or send schema-provided:

- `enum` values;
- `default` values;
- `example` / `examples`;
- `const` values;
- format-derived payloads.

Those would mix candidate discovery with semantic exploitation and remain outside this slice.

## First-pass isolation

Schema-typed candidates are isolated into one-candidate first-pass groups.

This is required because the historical group probe uses one generic value for every candidate in a group. Mixing a boolean probe with unrelated generic string candidates would make the experiment ambiguous.

The flow is therefore:

```text
OpenAPI response-only candidate
        ↓
single declared boolean/integer?
        ├── no  -> existing generic grouping/probe
        └── yes
              ↓
      isolate candidate
              ↓
 first pass with typed value
              ↓
 repeated candidate/control verification
```

## Candidate/control invariant

The paired random-name control receives the **exact same typed value and value kind** as the candidate.

Example:

```json
candidate: {"profile":{"beta_access":true}}
control:   {"profile":{"zz_pi_random":true}}
```

Only the leaf name differs.

A server that reacts to any unknown boolean field therefore produces candidate and control activity and is rejected by the existing confidence model.

## Audit output

When a finding is discovered using this path, the result records:

```text
discovery_mode: schema_typed
discovery_value: true
discovery_value_kind: boolean
```

Verbose output renders the same decision so the hunter can see that the OpenAPI declaration influenced the probe type.

## Safety and compatibility boundaries

Slice 3 does not:

- change confidence scoring;
- change evidence comparison;
- change the random negative-control rule;
- activate OpenAPI scaffolding;
- authorize additional state-changing requests beyond the existing CLI guard;
- use external OpenAPI references;
- use schema enums/defaults/examples;
- add arrays, objects, or multi-level JSON synthesis;
- alter non-OpenAPI candidate behavior.

OpenAPI-derived one-level scaffold descriptors remain withheld exactly as in Slice 2.
