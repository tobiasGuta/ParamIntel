# ParamIntel v0.5 Design: Rate-Limit Evidence Integrity

Status: design only

## Goal

Protect ParamIntel's evidence model from responses that are known to be rate-limited or server-backoff responses, and optionally pace requests so researchers can respect target limits without changing ParamIntel's sequential discovery architecture.

The core rule is:

> A response known to be rate-limited must never enter ParamIntel's behavioral comparator as evidence.

This is an evidence-integrity feature first and an operational-throttling feature second.

## Why this belongs in ParamIntel

ParamIntel's confidence model assumes candidate, control, baseline, characterization, and value-aware responses reflect application behavior closely enough to compare meaningfully.

A rate-limit response violates that assumption. If a 429 response is treated as an ordinary snapshot, ParamIntel may reason about throttling behavior instead of parameter behavior. Depending on when the limiter activates, that can corrupt group narrowing, candidate/control symmetry, characterization, or value-aware rescue.

The current request path ultimately funnels all active traffic through:

```text
baseline.Build
        \
baseline.SendMutations
        \
http.Client.Do
```

Discovery phases call the same helper:

```text
group probing
candidate verification
random controls
value-aware rescue
characterization
```

That shared HTTP boundary is the correct place to protect evidence globally.

## Non-goals

v0.5 does not add:

- automatic retry of POST/PUT/PATCH/DELETE requests;
- adaptive concurrency;
- distributed rate limiting;
- WAF fingerprinting;
- generic 403 classification as rate limiting;
- probabilistic rate-limit inference from arbitrary response text;
- automatic resume after a limiter clears;
- background waiting or scheduled continuation;
- target-specific rate-limit heuristics;
- per-candidate partial reports after evidence integrity is lost.

## Correct failure model

A normal application response can become a `model.Snapshot` and enter `compare.AgainstBaseline`.

A definite rate-limit/backoff response must not.

```text
HTTP response
    \
rate-limit classifier
    \
    +-- trusted application response --> read body --> Snapshot --> comparator
    \
    +-- definite rate-limit response --> typed error --> abort scan
```

This keeps the comparator unchanged.

## What counts as definite rate limiting

### HTTP 429

HTTP 429 is always classified as a rate-limit condition.

The error should preserve:

- status code;
- `Retry-After` raw value when present;
- parsed retry delay or absolute time when valid;
- request method and URL only if safe for diagnostics (never headers/body/tokens).

### HTTP 503 + Retry-After

HTTP 503 alone has many meanings. In v0.5, classify 503 as a server-backoff condition only when a valid `Retry-After` header is present.

This condition is treated equivalently for evidence integrity: the response does not enter the comparator.

### HTTP 403

Do not classify 403 as rate limiting in v0.5 solely from the status code.

403 can represent authorization denial, WAF behavior, business rules, anti-bot enforcement, or application logic. Guessing rate limiting from 403 would risk suppressing real behavioral evidence.

## Retry-After parsing

Support both standard forms:

```text
Retry-After: 10
```

and:

```text
Retry-After: Wed, 21 Oct 2015 07:28:00 GMT
```

Parsing rules:

- non-negative integer seconds are accepted;
- valid HTTP-date values are accepted;
- negative or malformed values are preserved as raw metadata but not trusted as parsed timing;
- parsing does not itself cause sleeping or retrying in v0.5.0.

## No automatic retry in v0.5.0

When a definite rate-limit/backoff response is observed:

```text
stop current HTTP experiment
    \
return typed error
    \
propagate through baseline/discovery
    \
abort scan
```

Do not automatically replay the request.

This is especially important for state-changing methods. ParamIntel already requires `-allow-state-changing`; hidden automatic retries would create a new side-effect model and should not be introduced casually.

Verbose/user-facing output should explain the condition clearly, for example:

```text
error: rate limit detected: HTTP 429 (Retry-After: 10s); response was not used as discovery evidence
```

For 503 with Retry-After:

```text
error: server requested backoff: HTTP 503 (Retry-After: 30s); response was not used as discovery evidence
```

## Proactive pacing

Add one CLI option:

```text
-delay 250ms
```

Meaning: minimum delay between outbound ParamIntel HTTP requests.

Initial design rules:

- default `0` to preserve current scan speed;
- no `-rps` alias in v0.5.0;
- pacing is global across baseline, discovery, controls, rescue, and characterization;
- waits must honor context cancellation;
- no extra sleep after the final request is needed;
- requests remain sequential; this is not a concurrency redesign.

## Central request abstraction

Do not duplicate pacing/rate-limit checks across discovery packages.

Preferred shape:

```go
type RequestPolicy struct {
    Delay time.Duration
}

type Sender struct {
    Client *http.Client
    Policy RequestPolicy
}

func (s *Sender) SendMutations(
    ctx context.Context,
    tmpl model.RequestTemplate,
    mutations []model.Mutation,
) (model.Snapshot, error)
```

However, the exact API should minimize churn in existing call sites.

A compatible alternative is to extend the existing baseline send layer with a small transport/policy object while preserving `baseline.Build` and the discovery engine's public behavior.

Important invariant:

> every ParamIntel HTTP request used for evidence must pass through the same policy object.

## Pacing semantics

The delay is a minimum interval between request starts, not an unconditional sleep before every request.

That distinction avoids compounding slow server latency unnecessarily.

Conceptually:

```text
request 1 starts at T0
request 1 completes at T0 + 400ms
configured delay = 250ms
request 2 may start immediately because >250ms elapsed
```

but:

```text
request 1 completes in 20ms
configured delay = 250ms
request 2 waits about 230ms
```

This provides predictable request-start pacing while preserving efficiency on already-slow endpoints.

### Context-aware wait

Never use an uncancellable bare `time.Sleep` in the evidence path.

Use a timer/select so cancellation terminates the scan promptly.

## Concurrency and state

ParamIntel is currently sequential, but the pacing implementation should still be race-safe under tests and future reuse.

If a sender stores the last request-start time, access should be protected appropriately.

No global package-level mutable limiter state.

Each CLI run owns its own sender/policy state.

## Typed error

Introduce a closed, inspectable error type rather than string matching.

Example shape:

```go
type BackoffError struct {
    StatusCode    int
    Kind          string // "rate_limit" or "server_backoff"
    RetryAfterRaw string
    RetryAfter    time.Duration
    RetryAt       time.Time
}
```

Exact fields can be refined, but callers/tests must be able to use `errors.As`.

The error string should not include request headers, cookies, authorization values, or request bodies.

## Baseline behavior

Rate limiting during baseline construction invalidates the baseline.

Example:

```text
baseline request 1 --> 200
baseline request 2 --> 429
```

Required result:

```text
baseline.Build returns an error
no BaselineProfile is accepted
scan does not begin
```

Do not build a baseline from the remaining samples.

## Group narrowing behavior

If any group probe receives a definite rate-limit response:

```text
groupInteresting --> typed error
narrow/ScanWithCandidates --> error
CLI --> abort
```

Do not interpret the group as interesting or quiet.

## Candidate/control verification behavior

If either half of a candidate/control experiment receives a definite rate-limit response, the experiment is invalid.

Examples:

```text
candidate --> 429
control --> not sent / irrelevant
```

or:

```text
candidate --> 200
control --> 429
```

Required result:

```text
no trial count is accepted as valid evidence
verification returns error
scan aborts
```

Do not decrement confidence or label the candidate rejected. The evidence is unavailable, not negative.

## Value-aware rescue behavior

A rate-limit response during semantic screening, same-value control, or repeated explicit-value verification must abort the scan.

Semantic budget accounting remains request accounting, not evidence accounting. If a request was actually sent before receiving 429, it may still count as consumed from the semantic request budget. This distinction should be documented/tested if implementation exposes it.

The rate-limit error takes precedence over the final budget diagnostic.

## Characterization behavior

If characterization encounters rate limiting after a parameter was already discovered, v0.5.0 should still abort the scan rather than silently return a partially characterized finding.

Reason: the CLI currently emits one final report after the scan. Introducing partial-success report semantics is a separate design decision and should not be smuggled into rate-limit handling.

Future work could distinguish discovery-complete/characterization-inconclusive, but not in the first implementation.

## Output behavior

v0.5.0 does not write a normal findings report when a definite rate-limit/backoff error aborts the scan.

The CLI exits non-zero and prints a concise diagnostic.

This avoids presenting partial findings as if the scan completed normally.

## CLI

New flag:

```text
-delay duration
```

Examples:

```text
-delay 0
-delay 100ms
-delay 250ms
-delay 1s
```

Validation:

- negative duration: error before any HTTP request;
- zero: disabled;
- positive: global request-start pacing.

No retry flags in v0.5.0.

## Versioning

Implementation release target:

```text
ParamIntel v0.5.0
```

The design-only branch must not change the CLI version.

## Required tests

### Request boundary unit/integration tests

1. 429 never becomes a Snapshot.
2. typed error is discoverable with `errors.As`.
3. Retry-After integer seconds parses correctly.
4. Retry-After HTTP-date parses correctly using an injectable/fixed clock where needed.
5. malformed Retry-After remains raw metadata but does not panic.
6. 503 + valid Retry-After becomes server-backoff error.
7. 503 without Retry-After remains an ordinary response.
8. 403 remains an ordinary response.
9. response body is closed for rejected 429/503 responses.

### Baseline tests

10. baseline receives 429 on one sample --> Build fails explicitly.
11. baseline receives 503 + Retry-After --> Build fails explicitly.

### Discovery integrity tests

12. group probe gets 429 --> scan errors; no narrowing decision is made from that response.
13. candidate gets 429 while control would be normal --> no finding; scan errors.
14. candidate normal, control gets 429 --> no finding; scan errors.
15. value-aware screen gets 429 --> no rescue finding; scan errors.
16. same-value semantic control gets 429 --> no rescue finding; scan errors.
17. characterization gets 429 after a valid finding --> scan errors; no normal report is returned.

### Pacing tests

18. `-delay 0` adds no intentional wait.
19. positive delay enforces minimum spacing between request starts.
20. slow responses do not receive unnecessary extra sleep once the request-start interval is already satisfied.
21. pacing wait exits on context cancellation.
22. pacing state is race-safe under `go test -race`.

### CLI tests

23. negative `-delay` is rejected before network activity.
24. `-version` reports v0.5.0 after implementation.
25. rate-limit CLI diagnostic states that the response was not used as discovery evidence.

### Regression gates

26. existing v0.4 `debug=true` value-aware regression still passes.
27. context + typed boolean `$.options.include_deleted` regression still passes.
28. dynamic/noisy JSON `limit` regression still passes.
29. GraphQL seeded `query` regression still passes.
30. contextual mass-assignment `$.chosen_discount` regression still passes.
31. entropy failure remains fail-closed.
32. semantic rescue budget remains deterministic and enforced.

## Acceptance labs

### Lab A: mid-scan 429 integrity

Controlled endpoint:

```text
first N requests --> normal application responses
next request --> 429 Retry-After: 2
```

Expected:

```text
ParamIntel aborts at first 429
429 response is never compared to baseline
no normal findings report is emitted
error includes parsed retry guidance
```

### Lab B: asymmetric candidate/control limiter

Controlled endpoint intentionally rate-limits one side of a paired experiment.

Expected:

```text
candidate/control experiment becomes invalid
no confidence score is produced from the pair
scan aborts
```

This specifically proves that v0.5 protects candidate/control symmetry.

### Lab C: pacing

Controlled server records request-start timestamps.

Run with:

```text
-delay 100ms
```

Expected:

```text
consecutive request starts are >= configured interval within reasonable scheduler tolerance
```

## Proposed implementation slices

### Slice 1 — typed backoff classification at the shared send boundary

Scope:

- typed `BackoffError`;
- classify 429;
- classify 503 only with valid Retry-After;
- parse Retry-After seconds and HTTP-date;
- reject classified responses before Snapshot construction;
- response-body closure tests;
- baseline failure regression;
- no CLI flag/version change yet.

Acceptance:

```text
429/503-backoff responses cannot enter compare.AgainstBaseline through the normal send path.
```

### Slice 2 — global request pacing

Scope:

- request policy/sender state;
- minimum interval between request starts;
- context-aware wait;
- race-safe state;
- `-delay` CLI flag;
- negative-duration validation;
- thread policy through baseline + discovery without duplicating logic.

Acceptance:

```text
all evidence-bearing HTTP requests use the same pacing policy.
```

### Slice 3 — discovery-phase integrity regressions

Scope:

- group 429;
- candidate 429;
- control 429;
- value-aware 429;
- characterization 429;
- explicit no-normal-report behavior at CLI boundary;
- clear diagnostics.

Acceptance:

```text
no discovery phase converts known limiter behavior into confidence/evidence.
```

## Decision summary

v0.5 is not primarily a courtesy throttle.

It protects the central scientific assumption behind ParamIntel's detector:

> candidate and control responses must be trustworthy application observations before they are allowed to influence a finding.

Rate-limited/backoff responses violate that assumption, so v0.5 should identify them at the shared HTTP boundary and fail closed before they reach the comparator.
