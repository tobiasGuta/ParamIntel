# ParamIntel v0.5: Rate-Limit Evidence Integrity

Status: implementation complete through Slices 1–3; release hardening complete; external Windows acceptance pending

## Goal

Protect ParamIntel's evidence model from HTTP responses that are known to represent rate limiting or explicit server backoff, and optionally pace requests without changing the existing sequential discovery architecture.

The core invariant is:

> A response known to be rate-limited or explicit server-backoff must never enter ParamIntel's behavioral comparator as evidence.

This is an evidence-integrity feature first and a courtesy-throttling feature second.

## Why this belongs in ParamIntel

ParamIntel's confidence model assumes baseline, candidate, random-control, value-aware, and characterization responses are trustworthy observations of application behavior.

A definite limiter response violates that assumption. Treating a 429 as an ordinary snapshot can make the tool reason about throttling rather than parameter behavior, including asymmetric candidate/control behavior.

All active HTTP traffic already converges on the shared send boundary:

```text
baseline.Build
        |
baseline.SendMutations
        |
http.Client.Do
```

Discovery phases use the same client/send path:

```text
group probing
recursive narrowing
candidate verification
random controls
value-aware screening
semantic controls
repeated semantic verification
characterization
```

Therefore v0.5 protects evidence below the discovery algorithms rather than duplicating limiter logic in every phase.

## Definite backoff classification

### HTTP 429

Every HTTP 429 is classified as:

```text
kind = rate_limit
```

The response is rejected before `model.Snapshot` construction.

### HTTP 503

HTTP 503 alone is ambiguous. v0.5 classifies it as:

```text
kind = server_backoff
```

only when a valid `Retry-After` header is present.

Therefore:

```text
503 + valid Retry-After
→ reject from evidence

503 without Retry-After
→ ordinary response

503 + malformed Retry-After
→ ordinary response
```

### HTTP 403

403 is not automatically classified as rate limiting. It can represent authorization, WAF behavior, anti-bot behavior, or application logic and can remain relevant evidence.

## Typed error

The shared baseline/send package exposes an inspectable typed error:

```go
type BackoffError struct {
    StatusCode      int
    Kind            string
    RetryAfterRaw   string
    RetryAfter      time.Duration
    RetryAt         time.Time
    RetryAfterValid bool
}
```

Callers/tests can use `errors.As` instead of parsing strings.

Diagnostics deliberately exclude request headers, cookies, authorization values, and bodies.

## Retry-After parsing

Supported forms:

```text
Retry-After: 10
```

and:

```text
Retry-After: Wed, 21 Oct 2015 07:28:00 GMT
```

Rules:

- non-negative integer seconds are accepted;
- valid HTTP dates are accepted;
- malformed values on 429 are retained as raw metadata;
- parsing does not automatically sleep or retry.

## Failure behavior

A definite backoff response follows this path:

```text
HTTP response
    |
backoff classifier
    |
typed BackoffError
    |
abort current experiment/scan
```

It never follows:

```text
HTTP response
    |
Snapshot
    |
AgainstBaseline
    |
confidence/evidence
```

### Baseline

If any baseline sample receives classified backoff, the baseline is invalid and scan startup fails immediately.

### Group/narrowing

A classified response during group probing returns an error. It is never interpreted as either an interesting group or a quiet group.

### Candidate/control verification

If either candidate or random-name control receives classified backoff, the pair is invalid. No partial confidence/trial result is returned.

### Value-aware rescue

A classified response during semantic candidate screening, same-value control, or repeated explicit-value verification aborts rescue and the scan.

Semantic request-budget accounting remains request accounting: a request actually sent before receiving 429 is still counted as used, even though its response is not evidence.

### Characterization

A limiter encountered after discovery but during characterization aborts the scan rather than silently returning a partially characterized normal report.

### CLI output

A rate-limit/backoff abort exits non-zero and does not write the requested normal findings report.

## No automatic retry in v0.5.0

v0.5.0 deliberately does not automatically replay requests after 429/503-backoff.

This is especially important for POST/PUT/PATCH/DELETE because ParamIntel already requires explicit `-allow-state-changing` acknowledgement. Hidden retry behavior would create a separate side-effect model.

Automatic retry/resume would require its own evidence and design.

## Global request pacing

New CLI flag:

```text
-delay 250ms
```

Meaning: minimum interval between outbound request starts.

Defaults:

```text
-delay 0
```

Rules:

- zero disables intentional pacing;
- negative values fail before network activity;
- pacing is shared globally by baseline and discovery;
- waiting honors context cancellation;
- pacing state is race-safe;
- no global package-level mutable limiter state exists.

### Request-start semantics

Pacing is not unconditional post-response sleep.

Example:

```text
request 1 starts T0
request 1 completes T0 + 400ms
-delay 250ms
request 2 may begin immediately
```

But:

```text
request 1 starts T0
request 1 completes T0 + 20ms
-delay 250ms
request 2 waits roughly 230ms
```

The implementation wraps the run's HTTP transport so every request using that client passes through the same request-start gate without changing discovery method signatures.

## Scope/non-goals

v0.5.0 does not add:

- automatic retry or resume after backoff;
- adaptive concurrency;
- distributed throttling;
- WAF fingerprinting;
- generic 403 rate-limit classification;
- probabilistic limiter inference from response text;
- target-specific limiter heuristics;
- partial-success report semantics;
- cache-aware probe correlation;
- server-side parameter pollution;
- missing-parent JSON scaffolding synthesis;
- array insertion;
- AI-generated values;
- Burp/MCP integration.

## Decision summary

v0.5 protects the scientific assumption behind ParamIntel's findings:

> candidate and control responses must be trustworthy application observations before they are allowed to influence confidence.

Definite limiter/backoff responses violate that assumption, so they fail closed at the shared HTTP boundary before comparison.
