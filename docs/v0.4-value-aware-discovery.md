# ParamIntel v0.4 Design: Value-Aware Discovery

Status: design only

This document defines the proposed ParamIntel v0.4 scope before implementation. It is intentionally narrow: improve discovery recall for real parameters that react only to meaningful values while preserving ParamIntel's existing negative-control and evidence-oriented trust model.

## Why v0.4 exists

ParamIntel v0.3 uses a generic random string during first-pass group discovery and individual verification. Candidate-specific semantic values are only tried later during characterization, after a candidate has already survived discovery and verification.

That ordering creates a reproducible false negative for value-sensitive parameters.

Observed benchmark:

```text
GET /api/users
→ baseline

GET /api/users?debug=<random-token>
→ baseline

GET /api/users?debug=true
→ meaningful response change

GET /api/users?zz_pi_random=true
→ baseline
```

`debug` is already present in ParamIntel's built-in candidate set and query placement is supported, yet v0.3 reports zero findings because the first discovery probe uses a random string. This is a probe-value selection failure, not a candidate-name, placement, baseline, or verifier failure.

## Goal

Allow ParamIntel to rescue candidates that are invisible to a generic random-string probe but react reproducibly to a small, conservative, candidate-appropriate set of values.

The feature must improve recall without turning semantic values into automatic findings and without weakening paired random-name negative controls.

## Non-goals

v0.4 does not add:

- server-side parameter pollution or parameter-within-parameter-value mutation;
- cache-key or cache-poisoning classification;
- arbitrary value fuzzing;
- large enum dictionaries;
- business-state values such as `admin`, `owner`, `paid`, or `production` unless they are themselves parameter names already under test;
- AI-generated values;
- Burp UI, MCP, cloud, or autonomous scanning integrations;
- candidate-name acquisition beyond the existing built-ins, wordlists, and v0.3 context-response intelligence;
- changes to the confidence formula unless implementation evidence shows the current model cannot represent value-aware verification correctly.

## Design principle

A semantic value is a reason to test a candidate, not evidence by itself.

Every value-aware finding must still demonstrate candidate-specific behavior that a paired random-name control using the same value does not reproduce.

```text
candidate=value
        vs
zz_pi_random=value
```

The comparison value must be identical on both sides of the pair.

## Proposed pipeline

v0.3 currently behaves conceptually as:

```text
candidate generation
  ↓
generic random-string group probe
  ↓
recursive narrowing
  ↓
generic random-string verification
  ↓
accepted candidate
  ↓
semantic characterization values
```

v0.4 should become:

```text
candidate generation
  ↓
generic random-string discovery path
  ↓
accepted survivors ───────────────────────────────┐
                                                  │
non-survivors eligible for semantic rescue        │
  ↓                                               │
bounded value-aware rescue pass                   │
  ↓                                               │
paired candidate/control semantic verification   │
  ↓                                               │
rescued survivors ────────────────────────────────┘
  ↓
normal result construction + optional characterization
```

The generic v0.3 path remains first because it is cheap and already works well for parameters such as `query`, `limit`, and context-derived JSON fields.

Value-aware discovery is a rescue path, not a replacement for the current algorithm.

## Eligibility

Only candidates with a non-empty conservative semantic profile are eligible for value-aware rescue.

Initial v0.4 profile sources should reuse the existing `semantics.ProfileValues` logic where appropriate.

Examples:

### Boolean-like names

Names already recognized as boolean-like, such as:

```text
admin
debug
internal
preview
verbose
test
include_deleted
enabled
is_*
has_*
can_*
allow_*
enable_*
show_*
```

Query/form values:

```text
true
false
1
0
```

JSON values:

```text
true       (JSON boolean)
false      (JSON boolean)
"true"     (JSON string)
"false"    (JSON string)
```

### Integer-like names

Names already recognized as integer-like, such as:

```text
limit
offset
page
page_size
*_count
*_limit
*_offset
*_size
```

Values:

```text
0
1
10
-1
```

For JSON, use actual numeric JSON values. For query/form, use string encodings.

### Small existing semantic profiles

Existing conservative profiles may also be eligible:

```text
format       → json, xml, html
sort/order   → asc, desc
include      → all, true, *
fields       → all, true, *
expand       → all, true, *
```

These should remain deliberately small. v0.4 must not become a general-purpose enum fuzzer.

## Rescue-pass algorithm

### Phase 1: Preserve current generic discovery

Run current grouping, narrowing, and generic random-string verification unchanged.

Track candidates that were not promoted to normal verification because their generic group probes were baseline-like, plus candidates that reached verification but failed because the candidate itself was baseline-like.

Do not rescue candidates rejected because random-name controls reproduced their behavior. A candidate that already demonstrated generic unknown-parameter equivalence should remain rejected rather than receiving more values that could amplify noise.

### Phase 2: Build eligible rescue targets

For each generic non-survivor:

1. obtain `semantics.ProfileValues(candidate.Name, candidate.Location)`;
2. if no values exist, skip;
3. deduplicate equivalent value/kind pairs;
4. cap the semantic profile to the existing conservative set;
5. preserve candidate provenance from v0.3 context-response intelligence.

### Phase 3: Cheap semantic screening

For each eligible candidate/value pair, send one candidate request:

```text
candidate=value
```

Compare it against the stable baseline.

If baseline-like, move to the next value without a control request.

If meaningful, immediately send the paired control:

```text
zz_pi_random=value
```

If the control is also meaningful, that value does not rescue the candidate.

If the candidate is meaningful and the control is baseline-like, mark that value as a semantic rescue signal and move to full repeated verification.

This preserves request efficiency by spending paired-control requests only on semantic values that produce an initial signal.

### Phase 4: Repeated semantic verification

For the first qualifying rescue value, run the normal number of verification trials using that exact value:

```text
trial N:
  candidate=value
  zz_pi_random_N=value
```

Use a fresh random control name per trial, as v0.3 already does.

The candidate value itself remains fixed across the verification trials so reproducibility measures the same behavior.

Do not combine evidence from different semantic values into one confidence calculation. A finding should be verifiable with at least one specific value on its own.

### Phase 5: Result construction

A rescued result should preserve the normal v0.3 fields and add explicit value-aware provenance so a researcher can tell why the parameter was discovered.

Proposed result additions:

```json
{
  "discovery_mode": "value_aware",
  "discovery_value": "true",
  "discovery_value_kind": "string"
}
```

For JSON booleans/integers, `discovery_value_kind` distinguishes typed values from strings.

Context-derived `candidate_sources` remain unchanged and can coexist with value-aware discovery metadata.

## Confidence model

Initial recommendation: do not change the confidence formula.

The existing score already answers the core question needed here:

- how reproducibly did the candidate change behavior?
- how often did the same-value random-name control change behavior?
- how many evidence kinds support the change?

The only difference is that `value` becomes semantic rather than random.

Example:

```text
debug=true
candidate: 3/3 changed
control:   0/3 changed
```

should be eligible for the same score as a generic probe with equivalent evidence.

The report must make clear that confidence applies to the observed candidate/value behavior, not to a calibrated probability that the parameter exists.

## Request-budget control

Value-aware rescue can multiply requests if applied carelessly. v0.4 should remain bounded.

### Baseline cost

Unchanged.

### Generic discovery cost

Unchanged from v0.3.

### Semantic rescue cost

For each eligible candidate:

- up to `P` one-shot candidate probes, where `P` is the small semantic profile size;
- a control request only when a one-shot candidate probe is meaningful;
- repeated candidate/control trials only for the first value that passes one-shot candidate/control screening.

With the current built-in list, only a subset of candidates have profiles. Most generic words therefore do not incur rescue cost.

### Recommended cap

Add a configuration-level maximum semantic rescue probe count for the entire scan, not only per candidate.

Proposed CLI flag:

```text
-value-aware-budget 64
```

A value of `0` could disable the feature if desired, but the preferred user-facing interface is described below.

When the budget is exhausted:

- stop adding new semantic rescue probes;
- preserve already-confirmed findings;
- emit a verbose diagnostic;
- do not silently exceed the configured request budget.

Do not count normal baseline/generic discovery requests against this dedicated rescue budget; it should describe additional v0.4 semantic work only.

## CLI design

Recommended:

```text
-value-aware=true
-value-aware-budget=64
```

`-value-aware` should default to `true` in v0.4 only if benchmarks show the additional request cost remains modest and predictable. Otherwise ship it default-off for v0.4.0 and reconsider after real-world use.

Design preference before implementation: default-on is acceptable only with a hard global budget and clear verbose diagnostics.

`-characterize` remains independent:

```text
-value-aware=true -characterize=false
```

must still allow semantic values to participate in discovery even though post-confirmation characterization is disabled.

This separation is important because value-aware discovery solves a discovery false negative; it is not merely characterization moved earlier.

## Verbose diagnostics

The tool should make rescue behavior visible without dumping every request.

Suggested summary:

```text
[*] Value-aware rescue
    eligible candidates: 8
    semantic probe budget: 64
```

On a rescued candidate:

```text
[+] debug (query)
    discovery: value-aware using "true" (string)
    candidate: changed 3/3
    control:   changed 0/3
    confidence: 100% HIGH
```

If a semantic value produces generic behavior:

```text
[-] preview=true (query)
    candidate behavior reproduced by random-name control
```

Per-value rejection logs should remain concise to avoid overwhelming normal verbose output.

## Negative-control rules

These are mandatory for v0.4:

1. Candidate and control use the exact same semantic value and value kind.
2. Control preserves the same location and JSON parent as the candidate.
3. Only the parameter name changes to a fresh `zz_pi_<token>` control name.
4. Contextual candidate provenance is removed from the control, as in v0.3.
5. A value that changes both candidate and random control must not rescue the candidate.
6. Repeated verification uses a fresh random control name for every trial.
7. Do not pool candidate successes across different semantic values.
8. Secure token generation continues to fail closed if entropy is unavailable.

## Interaction with grouping and recursive narrowing

Do not attempt to batch different semantic values into the existing generic group-probe algorithm in the first v0.4 implementation.

Reason:

```text
debug=true
limit=1
format=json
```

inside one request creates attribution ambiguity when the response changes. It would require value-aware group semantics and could turn a narrow feature into a substantial algorithm rewrite.

Instead:

- keep current generic grouping/narrowing unchanged;
- run semantic rescue only on eligible candidates that generic discovery did not prove;
- screen candidate/value pairs individually with the bounded budget.

This intentionally trades some additional requests for much clearer attribution and simpler correctness.

A later version could research semantic grouping if request cost becomes a demonstrated problem.

## Interaction with contextual candidates

Context-derived candidates from v0.3 remain first-class candidates.

If a contextual candidate fails generic random-string discovery but its name has a semantic profile, it may enter value-aware rescue.

Example:

```text
context response exposes:
  $.include_deleted

random-string probe:
  no change

semantic probe:
  $.include_deleted = true
```

The final result should retain both:

```text
candidate source: context_response_only_json_property
and
discovery mode: value_aware
```

This is valuable because candidate-name intelligence and candidate-value intelligence are complementary rather than competing systems.

## Interaction with type inference

Do not treat name-based semantic rescue values as proof of type.

Example:

```text
debug=true
```

may produce behavior, but that does not necessarily prove the server has a formal boolean schema.

Existing type inference rules remain:

- server validation response: high-confidence type evidence;
- parameter-name heuristic: weak type evidence.

A successful semantic value can be recorded as a working value without automatically raising `type_confidence`.

## Safety and state-changing requests

The existing `-allow-state-changing` gate remains authoritative.

Value-aware rescue adds requests, so for POST/PUT/PATCH/DELETE and other state-changing methods the existing explicit opt-in remains mandatory.

The semantic budget should be displayed in verbose output so the researcher understands the maximum additional probing caused by v0.4.

## Cache/environment boundary

v0.4 does not attempt to solve shared-cache interference discovered during the unkeyed-query-string benchmark.

A cache can make candidate and control probes observe the same cached object even when the origin behavior differs. That violates the independence assumptions of ParamIntel's experiment.

Future cache-awareness may inspect headers such as `Age`, `X-Cache`, or cache-key diagnostics, but that is deliberately separate from value-aware discovery.

## Acceptance tests

### A. Required local value-sensitive acceptance

Ground truth:

```text
GET /api/users
→ baseline

GET /api/users?debug=<random>
→ baseline

GET /api/users?debug=true
→ adds stable debug object

GET /api/users?random=true
→ baseline
```

v0.3 expected result:

```text
0 parameters
```

v0.4 required result:

```text
[+] debug (query)
    discovery: value-aware using "true" (string)
    candidate: changed 3/3
    control:   changed 0/3
    confidence: HIGH
```

### B. False-lead semantic control

Add another boolean-looking candidate, for example `preview`, where both:

```text
preview=true
zz_pi_random=true
```

produce equivalent generic behavior.

Required result:

```text
preview not reported
```

This confirms semantic values do not bypass random-name controls.

### C. Preserve dynamic-noise benchmark

The existing local dynamic endpoint with unstable `request_id` and `timestamp` plus a real `limit` parameter must still report only `limit` with candidate 3/3 and control 0/3.

v0.4 must not regress baseline stability filtering.

### D. Preserve GraphQL verifier benchmark

When `query` is supplied through a wordlist, the hidden GraphQL endpoint must still produce:

```text
query
candidate: 3/3
control:   0/3
status: 400 -> 200
HIGH
```

Value-aware rescue must not alter generic verification behavior.

### E. Preserve v0.3 contextual mass-assignment benchmark

Without `chosen_discount` in a custom wordlist:

- context response derives `$.chosen_discount`;
- candidate changes 3/3;
- random control changes 0/3;
- provenance remains `context_response_only_json_property`;
- final result remains high confidence.

### F. Context + value-aware combined acceptance

Create a controlled JSON endpoint where the context response exposes `include_deleted`, the normal write request omits it, a random string is ignored, and JSON boolean `true` changes behavior.

Required result:

```text
$.include_deleted
candidate source: context_response_only_json_property
discovery mode: value_aware
discovery value: true
discovery value kind: boolean
candidate: 3/3
control: 0/3
```

This proves v0.3 candidate intelligence and v0.4 value intelligence compose correctly.

### G. Budget acceptance

With more eligible candidates than the configured semantic budget:

- the scan must never exceed the dedicated semantic rescue budget;
- already-confirmed findings remain in the report;
- verbose output states that the rescue budget was exhausted;
- ordering remains deterministic so the same request/config tests the same rescue candidates first.

### H. Entropy failure regression

Existing fail-closed token tests remain required for both generic and value-aware control-name generation.

## Proposed data-model addition

Minimal addition to `model.ParameterResult`:

```go
type ParameterResult struct {
    // existing fields...
    DiscoveryMode      string `json:"discovery_mode,omitempty"`
    DiscoveryValue     string `json:"discovery_value,omitempty"`
    DiscoveryValueKind string `json:"discovery_value_kind,omitempty"`
}
```

Do not add a large generalized experiment graph in v0.4. The report only needs enough metadata to explain the accepted discovery path.

## Proposed implementation slices

### Slice 1 — semantic rescue primitive

- add discovery-value metadata to result model;
- expose deterministic semantic rescue profiles using existing semantics logic;
- implement one-candidate semantic screen + paired control + repeated verification;
- add the local `debug=true` regression test;
- no CLI budget yet beyond an internal default cap if necessary.

Acceptance: controlled `debug=true` test flips from v0.3 MISS to v0.4 PASS without weakening the random-name control.

### Slice 2 — bounded scan integration

- integrate rescue after generic discovery;
- deterministic eligible-candidate ordering;
- global rescue budget;
- verbose summary;
- CLI flags;
- preserve generic path behavior.

Acceptance: budget tests and existing GraphQL/dynamic-noise tests pass.

### Slice 3 — context + value composition

- ensure context-derived candidates can enter semantic rescue;
- preserve both candidate source and value-aware provenance;
- add JSON typed-value combined acceptance.

Acceptance: context-derived boolean-only parameter passes with typed JSON boolean and 0/3 random control.

### Slice 4 — documentation and external validation

- README v0.4 detection model;
- CHANGELOG and VERIFICATION updates;
- repeat real PortSwigger v0.3 benchmarks for regression;
- run the controlled value-sensitive acceptance externally using the built binary;
- independent review before merge.

## Decision summary

The benchmark campaign exposed several different limitations:

```text
GraphQL query
→ candidate acquisition limitation

server-side parameter pollution
→ placement-model limitation

shared cache lab
→ environmental independence limitation

debug=true
→ probe-value selection limitation

dynamic JSON noise
→ already handled successfully
```

Value-aware discovery is the best v0.4 target because it fixes a demonstrated false negative inside ParamIntel's existing core purpose without broadening the product into a different class of scanner.

The v0.4 objective is therefore:

> Preserve ParamIntel's evidence-oriented verification model while allowing a bounded set of candidate-appropriate values to rescue real parameters that a generic random-string probe cannot reveal.
