# ParamIntel v0.7: Evidence Fidelity

ParamIntel v0.7 improves how deterministic response behavior is observed after a candidate is probed. It does not broaden candidate generation, change the confidence formula, or make AI authoritative.

The release rule is:

> **Only response features that prove stable during baseline collection may become new evidence. Candidate-specific behavior must still survive ParamIntel's paired random-name negative control.**

## Why v0.7 exists

Before v0.7, JSON responses already had strong path-level comparison, but dynamic non-JSON responses could be harder to interpret. A meaningful HTML or header change could be missed when raw body bytes changed naturally between requests and response length stayed inside normal variance.

v0.7 adds a deterministic response-feature layer so ParamIntel can distinguish stable application structure from ordinary response noise.

## Baseline response profile

Each baseline snapshot can contribute the following observations:

- normalized `Content-Type`;
- text/non-text classification;
- line count;
- word count;
- conservative HTML classification;
- HTML structural hash and element count;
- eligible response-header fingerprints;
- existing status, body-length, body-hash, and JSON-path observations.

A feature is only trusted when baseline sampling establishes the required stability. If a feature is unavailable or unstable, it is not promoted into evidence.

## New v0.7 evidence kinds

### `content_type`

Emitted when normalized `Content-Type` was stable during baseline collection and the probe response changes it.

### `header_added`

Emitted when an eligible response header was never observed during baseline sampling and appears during a probe.

Only the header name is reported. Raw header values and internal fingerprints are not copied into finding evidence.

### `header_removed`

Emitted when an eligible header was stable during baseline sampling and disappears during a probe.

### `header_value_changed`

Emitted when an eligible header remained stable during baseline sampling but its fingerprint changes during a probe.

Only the header name is reported.

### `html_structure_changed`

Emitted for non-JSON responses when baseline HTML structure was available and stable, and a probe changes that structure or stops presenting as comparable HTML.

The structural model is intentionally conservative and does not rely on raw dynamic text values.

### `line_count`

Emitted for non-JSON textual responses when line count falls outside the stable baseline range plus a conservative tolerance.

### `word_count`

Emitted for non-JSON textual responses when word count falls outside the stable baseline range plus a conservative tolerance.

## Existing evidence remains authoritative

v0.7 is additive. Existing evidence kinds remain intact, including:

- `status`;
- `json_path_added`;
- `json_path_removed`;
- `json_value_changed`;
- `body_changed`;
- `body_length`.

When both baseline and probe are JSON, the path-level JSON comparator remains the primary body semantics. The new line-count, word-count, and HTML-structure paths are intentionally focused on non-JSON responses.

## Header privacy and noise boundary

Response-header comparison uses local deterministic fingerprints. Raw values are not emitted through the response-feature helper.

The implementation excludes sensitive, transport-level, and commonly noisy headers before evidence comparison, including categories such as:

- authorization and cookie headers;
- `Content-Length` and transfer/connection headers;
- `Date`, `Server`, `Server-Timing`, and cache metadata;
- common request/correlation/trace identifiers;
- `Content-Type`, which has its own normalized evidence path.

This prevents rotating infrastructure metadata from becoming findings while still allowing stable application-specific headers to contribute evidence.

## Negative-control model is unchanged

A new evidence type does not automatically make a parameter valid.

ParamIntel still performs repeated candidate verification and paired random-name controls. If generic unknown-parameter behavior reproduces the same application change strongly enough, confidence remains insufficient and the candidate is rejected.

That means v0.7 improves what ParamIntel can observe without changing the core attribution question:

> **Did this specific parameter cause reproducible behavior that a random unknown parameter did not?**

## Acceptance coverage

The v0.7 acceptance suite proves the following end-to-end behaviors:

1. **Same-size HTML structural change** — `preview` changes a stable HTML element while response length, line count, and word count stay effectively unchanged. ParamIntel confirms the candidate through `html_structure_changed`.
2. **Header-only behavior** — `verbose` adds `X-Debug-Mode` while leaving the response body unchanged. ParamIntel confirms it through `header_added` without reporting the raw header value.
3. **Rotating response noise** — dynamic request IDs rotate on every response and do not become evidence.
4. **Generic unknown-parameter noise** — an endpoint changes whenever any query parameter is present. ParamIntel reports zero parameters because the paired random-name control reproduces the behavior.
5. **JSON regression protection** — a JSON candidate changes a stable JSON path while a rotating `request_id` property remains ignored because it is unstable during baseline collection.

The reproducible localhost lab is in:

```text
labs/v0.7-evidence-fidelity/
```

## Deliberate v0.7 boundaries

v0.7 does not add:

- cache-buster orchestration or cache-aware probe correlation;
- evidence-level confidence weighting;
- normalized dynamic-text diffing;
- header or cookie parameter discovery locations;
- missing-parent JSON object synthesis;
- array insertion;
- AI-generated semantic values;
- automatic exploitation.

Those remain separate design decisions rather than being bundled into the evidence-fidelity release.
