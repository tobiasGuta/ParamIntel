# ParamIntel v0.9 Slice 2 — OpenAPI Candidate Bridge

Slice 2 activates only the safest subset of the passive OpenAPI descriptors introduced in Slice 1.

## Governing rule

> OpenAPI may propose an exact JSON field placement. The existing ParamIntel verifier remains the only authority that can report a behavioral finding.

## CLI

A hunter may supply a local OpenAPI document with:

```text
-openapi <path>
```

The file is read locally. ParamIntel does not discover, download, or follow remote OpenAPI documents. The parser continues to disable file and remote reference resolution.

## Admission boundary

Only descriptors with:

```text
placement = existing_parent
```

are converted into `model.Candidate` values and admitted to discovery.

Descriptors with:

```text
placement = one_level_scaffold
```

remain passive metadata in Slice 2. They are not converted into candidates and do not receive `JSONScaffoldParent` or any other mutation authorization.

The existing `-json-scaffold` option remains scoped to deterministic `-context-response` candidates. Supplying `-openapi` does not broaden that gate.

## Verification path

An admitted OpenAPI candidate follows the normal ParamIntel flow:

```text
local OpenAPI document
        ↓
schemaintel operation/schema selection
        ↓
response-only existing-parent descriptor
        ↓
model.Candidate with OpenAPI provenance
        ↓
normal discovery batching/narrowing
        ↓
repeated candidate trials
        ↓
paired random-name control
        ↓
report only candidate-specific behavior
```

No OpenAPI declaration can directly create a finding or raise confidence.

## Provenance

Verified findings preserve optional schema metadata in `candidate_sources`:

- `source`;
- JSON `path`;
- `declared_types`;
- `read_only`;
- `write_only`;
- `required`;
- `schema_ref`;
- source priority and reason.

These fields are explanatory metadata only. They do not affect confidence scoring.

## Deliberate false negatives

Slice 2 still uses ParamIntel's existing discovery probe values. A schema-declared boolean or integer field may therefore be missed by a strict server if the initial generic probe is rejected the same way as the random-name control.

That conservative false negative is preferable to letting schema metadata bypass the negative-control invariant. A later slice may consider deterministic schema-informed probe typing, but only if candidate and random controls remain type-symmetric.

## Not included

Slice 2 does not add:

- OpenAPI-derived parent scaffolding;
- enum/default/example spraying;
- raw schema values as payloads;
- endpoint enumeration;
- new confidence rules;
- new evidence rules;
- array insertion;
- multi-level object synthesis;
- external reference loading;
- remote specification discovery.
