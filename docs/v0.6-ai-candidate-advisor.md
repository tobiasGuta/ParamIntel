# ParamIntel v0.6 development: AI Candidate Advisor

## Goal

The AI Candidate Advisor is an optional candidate-acquisition layer. It proposes hidden parameter names from sanitized application structure, then hands accepted hypotheses to the existing ParamIntel discovery engine.

The AI provider does **not** produce findings, confidence, or vulnerability claims. Every accepted candidate still goes through ParamIntel's normal active probing, paired random-name controls, repeated verification, rate-limit/backoff evidence rules, and confidence threshold.

The v0.6 development rule is:

> AI may decide what is worth testing. Only ParamIntel's deterministic verifier may decide what behaved differently.

## Provider-neutral architecture

ParamIntel owns a small internal provider interface:

```text
request
  |
  v
baseline sampling
  |
  +--> deterministic baseline profile
  |
  +--> one already-collected response
           |
           v
     local structure sanitizer
           |
           v
     AI provider interface
       |        |       |
     Gemini   OpenAI   local/other
       |
       v
candidate hypotheses
       |
       v
local validation + budget
       |
       v
existing ParamIntel verifier
```

Gemini is the first adapter. Provider-specific request/response types stay inside that adapter so another provider can be added without changing discovery, mutation, comparison, confidence, or report logic.

The initial Gemini adapter uses the Gemini Interactions REST API directly rather than adding a Google SDK dependency.

## API key handling

API keys are never accepted as a literal CLI flag and are never written to findings reports.

For Gemini, the default environment variable is:

```text
GEMINI_API_KEY
```

PowerShell example:

```powershell
$env:GEMINI_API_KEY = "YOUR_KEY"
```

A different environment-variable name can be selected with:

```text
-ai-api-key-env MY_GEMINI_KEY
```

The flag contains only the environment-variable **name**, not the secret.

## CLI

The advisor is disabled by default.

Normal usage no longer requires a separate response file:

```powershell
.\paramintel.exe `
  -request .\burprequests\request.txt `
  -ai-advisor `
  -ai-provider gemini `
  -ai-candidate-budget 12 `
  -verbose
```

ParamIntel first performs its normal baseline. One response already collected during that baseline is reused as AI context after local sanitization. This adds no extra context request to the target.

Gemini defaults to `gemini-3.5-flash-lite`. A real localhost acceptance run completed the full ParamIntel pipeline in 2.50 seconds, proposed exactly one candidate (`include_archived`), ranked it at priority 95, and ParamIntel independently verified it at 3/3 candidate changes versus 0/3 random-name controls. In the same environment, `gemini-3.8-flash` exceeded the two-minute full-pipeline deadline, while tiny direct requests still took 64.3 seconds through Interactions and 98.8 seconds through `generateContent`.

The default therefore favors the smaller low-latency model for this narrow hypothesis-generation job. A heavier model remains available explicitly:

```text
-ai-model gemini-3.8-flash
```

Any provider-supported model can be selected without changing discovery or verification code:

```text
-ai-model <model-id>
```

The default AI provider request timeout is two minutes. ParamIntel remains stateless with `store:false`; it does not silently switch to background/stored execution or automatically retry timed-out requests. The timeout remains user-configurable:

```text
-ai-timeout 3m
```

When a different related response is intentionally more useful than the target's own baseline response, it can be supplied as an explicit AI-only override:

```text
-ai-context-response response.txt
```

The override is still sanitized locally before anything is sent to the provider. `-context-response` remains the separate deterministic context-intelligence input and is not implicitly substituted for the baseline AI context.

The JSON report records which source was used:

```json
"context_source": "baseline_response"
```

or:

```json
"context_source": "ai_context_response"
```

## Sanitized-input boundary

The AI adapter never receives the raw captured request, raw baseline response, or raw override response.

The local sanitizer keeps only bounded structural metadata useful for candidate generation:

- HTTP method;
- URL path with numeric IDs, UUIDs, long/unsafe path segments, and email-like segments replaced by placeholders;
- query parameter names, never query values;
- form parameter names, never form values;
- request JSON property names and primitive types, never primitive values;
- baseline/override response JSON property names and primitive types, never primitive values;
- valid JSON object parents where ParamIntel can actually insert a candidate;
- active discovery locations.

It intentionally omits:

- hostname;
- Authorization headers;
- Cookie / Set-Cookie values;
- API keys and bearer tokens;
- query/form values;
- JSON primitive values;
- raw response text;
- arbitrary headers.

Application-derived strings are still treated as untrusted data in the Gemini system instruction. Local validation rejects malformed names, unsupported locations, impossible JSON parents, already-present parameters, deterministic candidate names ParamIntel already covers, duplicate suggestions, and suggestions beyond the configured budget.

Only the static built-in candidate names are shared with the provider as exclusions. Names loaded from a user-supplied wordlist stay local while still participating in the local deterministic-coverage gate.

## Evidence boundary

An accepted AI suggestion is stored only as candidate provenance:

```json
{
  "source": "ai_semantic_hypothesis",
  "priority": 90,
  "reason": "response structure exposes archival state"
}
```

That provenance explains **why the candidate was tested**. It does not increase confidence.

A parameter appears in normal findings output only if the existing verifier independently demonstrates candidate-specific behavior against its controls.

## Failure behavior

AI provider configuration and API-key validation happen before target traffic begins. When AI is enabled, ParamIntel then performs its normal baseline, derives sanitized structural context from an already-collected baseline response (unless an explicit AI override was supplied), and calls the provider before discovery probing begins.

If the provider call fails, ParamIntel exits after baseline but before discovery. There is no silent fallback that would make an AI-enabled run look successful when the advisor did not actually execute.

Rate-limit/backoff responses remain ineligible as baseline evidence and therefore cannot become automatic AI context through the baseline path.

## First-slice boundary

This first v0.6 slice adds AI-generated **candidate names and placements** only.

It deliberately does not yet allow AI-generated semantic values to enter value-aware rescue. The existing curated semantic profiles and their request budget remain unchanged. A later slice can add provider-suggested values only if they are forced through the same-value random-name control and repeated-verification model rather than being treated as trusted model output.
