# v0.11 Static Rescue Scheduler Evaluation

## Scope

This evaluation compares the legacy v0.10 rescue order with the v0.11 static evidence-guided scheduler through the same discovery engine.

The verifier, semantic profiles, negative controls, repeated verification, confidence thresholds, and request budget are identical. Only rescue scheduling differs.

The comparison uses a dedicated engine switch:

- `EvidenceGuidedRescue=false` — legacy v0.10 order;
- `EvidenceGuidedRescue=true` — v0.11 static scheduler.

The production v0.11 CLI explicitly enables the new scheduler.

## Frozen scenarios

### 1. Context relevance under an 8-request budget

Candidates:

```text
debug
format
```

The response exposes `supported_formats`, making `format` contextually relevant. The hidden behavior is `format=json`.

Result:

| Scheduler | Finding | Rescue requests | Miss cost | Verified cost |
| --- | --- | ---: | ---: | ---: |
| v0.10 legacy | none | 6 | 6 | 0 |
| v0.11 guided | format | 8 | 0 | 8 |

The legacy scheduler spends four clean-miss requests on `debug`, then begins `format` but cannot reserve the six-request repeated-verification block. It stops after six used requests with two unusable requests remaining.

The v0.11 scheduler moves `format` first and converts the bounded budget into a verified finding.

### 2. Equal evidence, lower screening cost

Candidates:

```text
debug  -> four deterministic screening values
sort   -> two deterministic screening values
```

Both are local semantic heuristics. The hidden behavior is `sort=asc`.

Result:

| Scheduler | Finding | Rescue requests | Miss cost | Verified cost |
| --- | --- | ---: | ---: | ---: |
| v0.10 legacy | none | 6 | 6 | 0 |
| v0.11 guided | sort | 8 | 0 | 8 |

With otherwise equal evidence, the lower clean-miss screening cost lets v0.11 test the candidate that can still complete verification inside the budget.

### 3. Strong candidate already first

The hidden `format=json` candidate is already first in legacy order.

Both schedulers verify the same finding at the same rescue cost.

This protects against claiming a gain where ordering was already favorable.

### 4. Application evidence versus an AI candidate

Two seeded candidates are intentionally supplied in this order:

```text
debug   -> AI semantic hypothesis
format  -> application/context-response evidence
```

Both handlers are capable of producing a real behavioral change.

Legacy v0.10 spends the tight budget on the first-listed AI candidate. v0.11 spends it on the application-backed candidate.

This validates the scheduling contract rather than claiming higher raw finding count: deterministic target evidence outranks AI provenance.

### 5. Zero-signal 17-candidate control

The candidate set mirrors the semantic-profile mix from the earlier 17-candidate / 64-request rescue run:

```text
admin
debug
include
include_deleted
internal
limit
offset
page
page_size
preview
sort
order
format
fields
expand
verbose
test
```

The endpoint returns no meaningful response for any value.

Result:

| Scheduler | Findings | Rescue requests | Miss cost |
| --- | ---: | ---: | ---: |
| v0.10 legacy | 0 | 60 | 60 |
| v0.11 guided | 0 | 60 | 60 |

This is an important negative result.

Static evidence-guided ordering does **not** reduce request waste when all candidates are weak and the endpoint provides no useful signal. It only changes order.

## Conclusion

The static scheduler earns its place because it improves bounded-budget recall in the controlled positive scenarios without regressing the already-favorable case.

However, it does not satisfy the request-reduction objective on zero-signal endpoints.

The next adaptive slice is therefore justified, but it must be evaluated as an explicit recall/cost tradeoff rather than assumed to be an improvement.

## Gate for adaptive depth

High-evidence candidates (tiers A/B) must retain full deterministic semantic profiles.

Any reduced-depth behavior should initially apply only to low-evidence local/generic candidates and must be tested against fixtures where the valid behavior occurs on later profile values.

The adaptive slice passes only if its request savings are material and the measured recall loss is zero or small enough to justify the tradeoff. It must remain observable and reversible until that evidence exists.


## Safe adaptive tail guard

After freezing the static comparison above, v0.11 added one conservative adaptive rule:

> Do not start another semantic value when the remaining request budget is smaller than the minimum needed to screen that value, run its paired control, and complete repeated verification.

With three verification trials, the minimum actionable budget is:

```text
1 candidate screen
+ 1 paired control
+ 3 candidate verification requests
+ 3 control verification requests
= 8 requests
```

This does not truncate a value profile while a new finding could still be fully verified. It only prevents requests that cannot possibly produce an admissible ParamIntel finding under the current remaining budget.

The 17-candidate zero-signal control changes from:

| Scheduler | Findings | Rescue requests | Miss cost |
| --- | ---: | ---: | ---: |
| v0.10 legacy | 0 | 60 | 60 |
| v0.11 static only | 0 | 60 | 60 |
| v0.11 + verification floor | 0 | 57 | 57 |

That is a 5% reduction versus the legacy zero-signal cost, achieved without dropping a finding that remained verifiable within the configured 64-request budget.

The audit outcome is reported as `verification_budget_insufficient`, not literal budget exhaustion, because unused requests can remain even though they are insufficient to complete a new finding.

## Current evaluation verdict

The controlled suite supports keeping the v0.11 scheduler:

- positive tight-budget scenarios improve from no verified finding to a verified finding;
- already-favorable ordering does not regress;
- deterministic application evidence outranks AI provenance as designed;
- zero-signal behavior is not misrepresented as a large cost win;
- the safe tail guard removes only requests that cannot complete verification.

The measured benefit is primarily **better allocation of a bounded request budget**, with a small additional zero-signal tail saving. The evidence does not justify aggressive semantic-profile truncation, so v0.11 should not add one by default.
