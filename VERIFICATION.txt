Core v0.4 behavior:
- existing random-string batch/narrow discovery remains the first-pass detector
- value-aware discovery is a bounded rescue pass for clean generic misses
- semantic candidate probes are paired with same-value random-name controls
- candidate/control value kind and value remain identical; only the parameter name changes
- evidence from different semantic values is never pooled
- repeated explicit-value verification still uses the standard confidence model
- -value-aware defaults to true
- -value-aware-budget defaults to 64 additional requests
- the semantic budget reserves complete repeated-verification cost before confirmation begins
- the semantic budget never exceeds the configured cap
- exact final budget consumption is reported as exhausted
- candidates with generic candidate/control activity are not reinterpreted by semantic rescue; only clean misses are eligible
- -characterize=false does not disable value-aware discovery
- findings record discovery_mode, discovery_value, and discovery_value_kind

Manual acceptance conclusion:
- v0.4 fixes the demonstrated probe-value-selection false negative without changing the candidate list, placement model, confidence threshold, or negative-control philosophy.
- the improvement comes from trying bounded semantic values earlier in discovery, not from weakening verification.

Request-efficiency review:
- the default 64-request semantic cap can be fully consumed even with a modest candidate set
- no semantic profile values were removed solely to reduce request count because that would reduce recall for applications accepting only one representation such as true/false/1/0
- bounded request cost remains controlled by the global semantic budget pending future evidence for safer optimization

Known benchmark boundaries retained from pre-v0.4 testing:
- hidden GraphQL query default acquisition miss is a candidate-acquisition limitation, not a verifier failure
- server-side parameter pollution inside another parameter value remains outside the current query/form/JSON placement model
- shared intermediary caching can violate probe independence and requires separate cache-aware design rather than ad hoc changes in v0.4

Scope boundary:
- v0.4 does not add cache-awareness, server-side parameter-pollution mutation, missing-parent JSON scaffolding synthesis, array insertion, AI-generated values, Burp/MCP integration, or broad business-state enum spraying.
- ParamIntel findings remain research leads requiring manual authorization, impact, and exploitability validation.
